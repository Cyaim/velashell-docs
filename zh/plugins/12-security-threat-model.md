# 12 · 安全与威胁模型

> **现状限定**：下面 v1 强度表/威胁缓解表是蓝图目标，不是对当前全部插件运行模式的安全保证。当前仍有 inProcess 插件，`PluginPermissionGate` 仅覆盖 `terminal.write` / `session.open`；不能从 sudo 的专用宿主确认推出“所有能力经通用 Broker/完整进程隔离/审计均已实现”。本次实际边界见 §1.1。

## 1. 信任模型(分层陈述,禁止夸大)

| 资产 | v1 保护强度 | 依据 |
| --- | --- | --- |
| SSH 凭据(密码/私钥/passphrase) | **强**:物理上只存在于宿主进程与 OS 凭据库,无任何 RPC 可读取 | D5 |
| 会话通道(SFTP/exec/终端) | **强**:仅经宿主能力 API 可达,每次调用过 Broker,可撤销、有审计 | 06 |
| 宿主 UI 与其它插件 | **强**:进程隔离 + UI 全部宿主渲染;插件间无通道 | D1/D6 |
| 插件私有数据 | **中**:目录按插件划分 + secrets 命名空间隔离;同一 OS 用户下无强制隔离 | — |
| 本地文件系统 | **弱(v1)**:经 API 的访问受 Broker;但插件进程可直接 syscall 绕过 | 见 §3 |
| 网络出口 | **弱(v1)**:声明制 + SDK 审计;无物理拦截 | 见 §3 |

结论:v1 的安全承诺是"**插件拿不走你的凭据、碰不了你的服务器(除非
授权)、搞不垮你的主程序**";"恶意插件不能读你本地磁盘"在 v1 **不成
立**,靠来源信任(签名分档,见 10)把关。此表在用户文档与插件安装
确认页如实呈现。

### 1.1 此次 sudo 与 AI 托管执行的实际边界（SDK 2.1.0）

- 专用 `StreamSudoAsync` 只有目标、实际命令和非敏感选项；来源插件绑定宿主清单，目标取真实连接。宿主每次先确认**整条 root 命令（含管道/重定向）**，NOPASSWD/缓存有效也一样；插件审批的 Bypass 不能跳过宿主确认。密码输入不是命令授权。
- 密码只在宿主可信遮罩 UTF-8 输入框取得，不默认取 SSH 登录密码、不记忆；禁 CR/LF/NUL/控制字符，禁 undo，使用后清理可控缓冲与控件。受控 PTY 确认禁回显、匹配一次性提示且处在认证阶段才发送，最多三次密码应答、总认证等待两分钟；命令启动后应答入口不可逆关闭、stdin 关闭。无 UI/不支持的 PTY/PAM/OTP 明确失败，不在插件内询问、不绕 sudoers 限制、不重跑普通命令。用户命令的完整原始启动标记不能直接出现在 sudo 可回显的 argv 中，须由真正获准启动的 root 包装进程生成；策略拒绝的诊断回显不能制造 Running/Exited 或泄漏认证尾部。真实互操作曾发现并修复此客户端状态误判，不是 sudoers 授权绕过。随机标记不能防御已经被攻陷的远端。
- 密码与原始认证阶段内容不得进入插件/模型、RPC、历史、磁盘、日志、工具卡或 Bridge/MCP。连接级引用计数租约在敏感期间抑制**所有通道双向 payload**，保留必要元数据且不改用户诊断设置；要等对端 CLOSE 与发送泵排空或连接结束，不能以 Dispose 返回推断安全。开通道失败拿不到可跟踪通道时，保守抑制至连接结束。详见 [SSH 规格 §9.1](../ssh/spec/08-failures.md#91-敏感交互的连接级载荷抑制租约)。
- 托管任务绑定入口/对话/run、固定 sessionId；MCP 客户端隔离，查询/启动/完成重验 scope，清理取消不受读取授权撤销阻挡。**现有撤权限制**：`ISessionScope` 没有 Changed/撤权事件且组成员查询有 5 秒缓存；MCP/Bridge 设置 reload 会取消旧 run，但普通会话树分组成员变更若未触发 reload，仅在上述检查点复验，不能承诺密码框期间即时撤权。
- 插件审批拒绝/缺 Handler 与宿主 AuthenticationCancelled 都将当前 run 置为已拒绝，模型步骤、工具调用及后台续接强制 `ExecutionDenied` 暂停，不仅返回劝阻字符串；桌面/Bridge 新用户轮次须新 run；MCP 每客户端 host 使用固定 scope，后续工具继续拒绝（仅 `task_cancel` 清理），不是下一条 HTTP call 就复位，需新 host/session 或重新连接/刷新授权配置取得新 scope。Stop/入口销毁/卸载与隔离连接断开会取消并异步收尾；取消请求不保证远端已停止。Unknown、缺失退出码、已启动超时且未确认停止禁止自动推进/副作用重放。此功能不是用户终端自动填充，不修改已有终端凭据交互决定，也不支持 su/任意 stdin 或跨重启恢复。

SDK 2.1.0 已正式发布并用于宿主/AI，执行 RPC、Capability 及 sudo 参数化回归已通过；Ubuntu/Debian 的真实 sshd/PTY/PAM 执行内核矩阵（含重试、取消、策略拒绝）已通过。宿主 sudo 对话框及相关本地化/调度/样式门禁已通过（不是全 UI 套件），最新拒绝守卫后的全 AI、SSH 与严格构建结果仍待汇总；真实内核不等于 GUI 与插件 IPC 整链真实验收，认证超时/迟到租约综合动态范围不能自行扩大。当前发布/验证边界见 [自动化与 AI §1.4](11-automation-and-ai.md#14-ai-插件的托管执行与恢复sdk-210)。

## 3. OS 级沙箱路线(v2+,预研项)

目标:把 §1 的两个"弱"升为"中/强",让 fs.local/network 权限获得物理
强制。按平台可行性排序:

| 平台 | 手段 | 预判 |
| --- | --- | --- |
| Linux | Landlock(文件范围)+ seccomp(syscall 面收敛)+ cgroups v2(资源) | 最可行,内核 ≥5.13 |
| macOS | `sandbox_init` profile(Apple 半私有但 Chromium 等在用)或 App Sandbox 化的 helper | 可行,需打磨 |
| Windows | Restricted token + Job Object 起步;AppContainer 为终态(管道 ACL 需配套放行) | 工作量最大 |

原则:沙箱是**能力收敛器**而非权限系统替代——Broker/授权 UX 不变,
沙箱把"合规契约"变成"物理不可为"。路线图上 M8 启动预研,先 Linux。
