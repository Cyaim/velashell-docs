## 0. 结论先说

**已定决策（2026-09-15）**

| 项 | 定稿 |
|---|---|
| 抽象 | 新增 `ICredentialProvider`（凭据**来源**），**不**改造 `ISecretProtector`（凭据**加密**） |
| 首批 provider | 1Password（`op`）、Bitwarden（`bw`）、KeePassXC（`keepassxc-cli`）**三家一起交付** |
| 私钥 | **走 SSH Agent**，不经 CLI 取私钥。等上游 PR 合并后另行实施 |
| 引用粒度 | **整条配置绑定一个条目**；高级选项允许用本配置的用户名覆盖条目用户名 |
| 解锁口令 | **内存 TTL 缓存**，时长可配置 |
| 解析失败 | **退回登录弹窗 + 顶部提示条** |
| 引用与已存密码 | **禁止并存** |
| 形态 | **宿主内置**，不开放插件 SDK 契约 |
| 与 `IMasterKeyStore` | **并行推进**；系统密钥链 provider 等它的 P/Invoke 层 |

**v2 新增的关键结论**

1. **明文密码有三种载体、五个构建点**，不止 `BuildChainAsync` 一处（§2.1）。FTP 和三类插件协议都不经过 `ConnectionWorkflowService`，解析器必须接到每一个构建点上。
2. **发现四处既有缺陷**（§3），其中一处会让「记住密码」没勾时，用户手输的密码照样被写进数据库。建议作为**阶段 0a** 单独修掉，否则本功能的「引用配置不落盘密码」会建在一个漏水的地基上。
3. **自动重连不能弹解锁框**。网络恢复后 N 个标签同时重连，会同时触发解锁。解析要区分交互式与非交互式（§5.7）。
4. **「引用配置不落盘密码」这条不变量放在仓储层强制**。仓储是所有保存的唯一出口，比在各个调用点逐一防守可靠（§5.4）。
5. **1Password 在 Windows 上按进程链授权，而且这一点没有明确文档**。VelaShell 拉起 `op` 会不会每次都弹 Windows Hello，是阶段 1 的**第一个实测项**，结果直接决定调用次数的设计（§8.1）。
6. **Bitwarden 的 `bw list items` 会连同密码一起输出**；**KeePassXC CLI 只能按路径寻址，标题重名时取第一个匹配项**（§8.2 / §8.3）。

## 1. 纠正一个前提

`feature-plan.md` 原先的表述是：「`ISecretProtector` 就是那层抽象，加一个 `ICredentialProvider` 让它可插拔即可」。这句话只对了一半。

- `ISecretProtector` 管的是**怎么加密**：一个同步的 `string → string` 变换。
- 凭据管理器集成管的是**秘密放在哪、归谁管**：配置里存引用，而不是值。

两者是不同维度，不能共用一个接口：

| 若让 `ISecretProtector` 去调 `op` / `bw` | 后果 |
|---|---|
| `GetAllSessionsAsync()` 每次加载都对**所有**配置调 `Unprotect`（`SonnetDbSessionRepository.cs:38`） | 启动、刷新会话树时起 N 个 CLI 进程，可能连弹 N 次生物识别 |
| 接口是同步的，调用方有 5 处（会话、Gist PAT、两处插件机密、插件信任） | 要么全仓传染 async，要么在 UI 线程上阻塞等外部进程 |
| `PluginTrustRepository` 靠 AES-GCM 认证标签做完整性边界（`PluginTrustRepository.cs:37`） | 换成外部保险库后，这道边界不复存在 |
| `Unprotect` 解不开时**原样返回输入**（`AesSecretProtector.cs:79`） | 解析失败时，`op://vault/item` 会被当作密码发给远端服务器 |

正确的结构是两道接缝，各管一层：

```
                ┌──────────── 接缝 B：凭据来源（本文） ───────────────┐
 SessionProfile │ 存「引用」CredentialReference {provider, item}      │
                │        │ 连接那一刻才解析                           │
                │        ▼                                            │
                │ ICredentialProvider ─ 1Password / Bitwarden /       │
                │                       KeePassXC / 系统密钥链        │
                └─────────────────────────────────────────────────────┘
                ┌──────────── 接缝 A：主密钥存放（密钥链调研阶段 0/1）─┐
 已存的密码     │ ISecretProtector（不改） ← IMasterKeyStore           │
                │                            ├ DPAPI / Keychain /     │
                │                            └ libsecret / 文件回退   │
                └─────────────────────────────────────────────────────┘
```

「与系统密钥链调研是同一件事的两个入口」在这里的具体含义：

- 调研阶段 0/1 的 **`IMasterKeyStore`** 保护的是 VelaShell **自己存下的**密文，与本文互不依赖，并行推进。
- **系统密钥链作为 `ICredentialProvider`**，是让用户引用自己在系统凭据管理器里**已有**的条目。它与 `IMasterKeyStore` 共用同一层 P/Invoke，所以排在后面。
- 调研**阶段二（sudo 填充）**的凭据选择器，直接复用 provider 的 `SearchAsync` / `ResolveAsync`。

## 3. 顺带发现的既有缺陷

这四处与凭据管理器无关，今天就存在。但本功能会放大其中几处，所以**建议作为阶段 0a 单独修掉**（§16 N1）。

### D1 · 「记住密码」没勾，手输的密码仍可能落盘

**复现路径**（按代码推演，**待实测确认**）：

1. 某配置 `RememberPassword = false`，库里没有密码。
2. 用户在会话树上双击连接。`RequiresCredentials` 为真，弹出登录弹窗，用户输入密码且保持不勾「记住」。
3. 弹窗把密码写进**会话树缓存里的那个实例**（`MainWindow.axaml.cs:1533`）。连接成功后，workflow 按「记住密码」规则剥离密码再保存，这一步没有问题。
4. 用户随后把这条配置**拖进另一个分组**。`MoveSessionToGroupAsync` 直接保存缓存实例（`SessionTreeViewModel.cs:443`），**密码被加密写进数据库**。
5. 同理，「复制配置」（`:625`）、FTP / 插件证书信任后的 `PersistProfileIfSavedAsync`（`:4519`）也会把手输密码落盘。

**影响**：违背用户的明确选择。凭据被静默持久化，而且界面上看不出来。

**修法**（与 D3 一起修）：

- 登录弹窗改为**返回副本**，不再修改传入实例。
- 失败卡片的「重试」闭包改为捕获最新的 `current`，保留今天「重试不用重输」的体验。
- `PersistProfileIfSavedAsync` 改走 workflow 的剥离逻辑。
- 弹窗不再修改共享实例之后，会话树缓存里只剩仓储读出来的值（本来就已落盘），`MoveSessionToGroupAsync` 与复制配置自然不会再多存东西，**不必逐个改**。

### D2 · `WithPersistablePasswordAsync` 不剥离私钥口令

- `:144` 只写了 `stripped.Password = null`。
- 配置弹窗的「记住密码」勾选框只在密码认证时显示（`ConnectionProfileView.axaml:531-546`，受 `ShowPasswordField` 控制）；登录弹窗的私钥分支也不回写 `RememberPassword`。所以私钥口令**事实上总是会落盘**。
- 这可能是有意为之（口令在配置页填写，默认就该保存），也可能是遗漏。**需要你确认语义**（§16 N2），再决定是补上剥离，还是在注释里写明「口令不受记住密码控制」。

### D3 · 登录弹窗就地修改共享实例

见 §2.4。除了造成 D1，还会让明文密码散落在会话树缓存、命令面板缓存、隧道面板列表里，直到下次刷新。修法与 D1 相同。

### D4 · `SshSession.ConnectionInfo` 长期持有全部跳板密码

- 会话存活期间，`SshSession.ConnectionInfo` 一直保存完整的 `ConnectionInfo`，包括每一跳的密码与私钥口令，而读取方只用 Host / Port / Username（§2.6）。
- **修法**：`SshConnectionService.ConnectInternalAsync` 把 `ConnectionInfo` 交给 client 工厂之后，给 `SshSession` 挂一份**去掉机密的副本**（递归处理 `JumpHost`）。
- 这是低风险的加固。与本功能的关系：解析出来的保险库密码也会进入 `ConnectionInfo`，不加固的话它会驻留整个会话生命周期。

### 5.5 解析点：五个构建点逐一接线

| # | 构建点 | 改法 |
|---|---|---|
| 1 | `ConnectionWorkflowService.BuildChainAsync` | 构造函数新增可选的 `ICredentialResolver? credentialResolver = null`。每一跳：`profile.CredentialSource != null` 且内存中 `Password` 为空时，调用 resolver 填进 `ConnectionInfo.Username` / `Password`。**不回写 profile**。`ConnectProfileAsync` 与 `TestConnectionAsync` 增加 `CredentialResolveOptions` 参数（默认交互式） |
| 2 | FTP：`MainWindowViewModel.cs:3684` | 构建 `FtpConnectionInfo` 之前先解析。`FromProfile` 新增重载 `FromProfile(SessionProfile, ResolvedCredential?)` |
| 3 | `PluginProtocolFileService.OpenSessionCoreAsync` | 构造时注入 resolver（Infrastructure 内部，DI 可得）。组装 `ProtocolConnectRequest` 前解析 |
| 4 | `PluginTerminalShellStream` | 同上。它的重连也经过这里 |
| 5 | `PluginWorkspaceLauncher.OpenCoreAsync` | 同上 |

**优先级规则**：**内存中非空的 `Password` 优先于引用**。

- 弹窗手输的密码存在于本次连接的副本里（D1/D3 修好之后），自然生效。
- 仓储读出来的实例因为 §5.4 的不变量，永远不会同时有引用和密码。
- 所以这条规则只在「本次手输」时起作用，不会产生歧义。

**跳板各跳**：跳板配置从仓储读取，带引用就用**当前这次连接的交互模式**去解析。

- 解析失败时**不弹登录弹窗**（今天跳板也从来不弹），直接以连接错误结束。
- 错误信息写明是哪一跳的哪个 provider 出了问题，例如「跳板 bastion-01：Bitwarden 保险库已锁定」。

### 5.6 解析器内部行为（`CredentialResolver`）

1. **找 provider**：按 `ProviderId` 查找；未注册或在设置里被禁用时抛 `ProviderDisabled`。
2. **单次尝试缓存**：以「连接尝试令牌 + 引用」为键缓存 `ResolvedCredential`，尝试结束（成功或放弃）即丢弃。
   - 这样同一次尝试里，SSH 跳板链、重试循环中的非认证错误都不会重复查保险库。
   - 实现上，令牌由 `TryConnect*` 循环创建，经 `CredentialResolveOptions` 传下去；也可以用 `AsyncLocal` 承载，实施时取其简单者。
3. **按 provider 串行化解锁**：每个 provider 一把 `SemaphoreSlim(1,1)`。
   - 启动恢复 10 个标签、跳板多跳命中同一个锁定的保险库时，只弹一次解锁框，其余等待后复用同一个解锁会话。
   - 用户取消后，排队的其余请求**立即以 `UnlockCancelled` 结束**，不再逐个弹框。
4. **不缓存解析出的密码**：跨尝试（例如一小时后手动重连）会重新解析。保险库的解锁会话还在 TTL 内，就不会弹框。
5. **用户名规则**：`OverrideUsername` 为 true 时用 `SessionProfile.Username`，否则用条目用户名。两者都为空时抛 `MissingField`。

### 5.7 交互式与非交互式解析

| 触发来源 | 模式 | 保险库锁定时 |
|---|---|---|
| 用户主动连接：会话树、命令面板、最近连接、配置弹窗「连接」/「测试」、克隆标签、打开 SFTP / FTP / 插件文档、外部拉起、启动时恢复会话 | **交互式** | 弹解锁框 |
| 手动重连：Ctrl+R、回车、提示气泡上的「重连」按钮（`:872`、`:1246/2259`、`:2782`） | **交互式** | 弹解锁框 |
| 自动重连：`OnTabDisconnected` 定时器（`:2812-2832`）、`ReconnectAllAfterResume`（`:2694-2713`）、隧道 `AutoReconnectAsync` | **非交互式** | 抛 `Locked`，标签显示失败覆盖层，文案为「保险库已锁定，按 Ctrl+R 重连」 |
| 连接诊断 | 交互式（用户主动打开） | 弹解锁框 |
| 插件 `Sessions.OpenAsync` | 交互式（宿主本来就会弹确认框） | 弹解锁框 |

改动点：`ReconnectTabAsync` 增加参数 `bool interactive`，由各调用方传入；`TunnelPanelViewModel.AutoReconnectAsync` 传 `false`。

### 5.8 失败回退接线（决策 5）

**五个重试循环的改法相同**：

```csharp
catch (CredentialProviderException ex) when (InteractiveAuthenticator is not null)
{
    pendingNotice = CredentialNotice.From(ex);   // 带到下一次弹窗
    tab?.MarkConnectionFailed(...);              // SSH 终端路径
    continue;                                    // attempt > 0 → 必然弹窗
}
```

- **登录弹窗**：`AuthenticationDialogViewModel` 构造函数新增 `CredentialNotice? notice = null` 与 `bool hideRememberPassword = false`；`InteractiveAuthenticator` 委托签名相应扩展（或增加一个带选项的重载）。
- **没有弹窗委托的路径**（例如隧道面板里无委托的情况、非交互重连）：把异常转成本地化的连接错误文案，走现有的失败覆盖层或气泡。
- **手输密码仅本次有效**：带引用的配置在登录弹窗里隐藏「记住密码」。即使弹窗结果带回 `RememberPassword = true`，仓储不变量也会剥掉密码。
- **服务器拒绝了保险库给的密码**（`VelaSshAuthenticationException` 等）：沿用原有的认证失败重试。弹窗提示条写「来自 {provider} 的密码被服务器拒绝，条目可能已过期」。下一次尝试用用户手输的密码，**不再查保险库**（优先级规则，§5.5）。

**提示条内容**：

| `CredentialFailure` | 文案要点 | 附加操作 |
|---|---|---|
| `NotInstalled` | 未找到 {provider} 命令行工具 | 「打开设置」→ 定位到凭据页 |
| `ProviderDisabled` | {provider} 已在设置中停用 | 「打开设置」 |
| `NotSignedIn` | {provider} 未登录（1Password：请在 App 的「设置 → 开发者」开启 CLI 集成；Bitwarden：请先在终端执行 `bw login`） | — |
| `Locked` / `UnlockCancelled` | 保险库未解锁 | 「重试解锁」 |
| `UnlockFailed` | 解锁口令错误 | 「重试解锁」 |
| `NotFound` | 条目已不存在（可能被删除、移动或重命名；KeePassXC 按路径寻址，改标题也会找不到） | 「重新选择条目」→ 打开配置页 |
| `Ambiguous` | 找到多个同名条目（KeePassXC） | 「重新选择条目」 |
| `MissingField` | 条目缺少用户名或密码 | — |
| `Timeout` | {provider} 响应超时（1Password 可能在等待 Windows Hello 确认） | 「重试」 |
| `Malformed` | {provider} 返回了无法识别的结果，可能是版本不兼容 | 「打开日志目录」 |

### 5.9 解析值在内存中的去向

| 载体 | 驻留 | 处理 |
|---|---|---|
| `ConnectionInfo` → `SshSession.ConnectionInfo` | 会话生命周期 | 修 D4 之后去掉机密 |
| `ConnectionInfo` → `TmdsSshClientWrapper._settings` | 会话生命周期 | Tmds.Ssh 内部，维持现状（与手输密码相同） |
| `FtpConnectionInfo` → `FtpConnectionPool` | 连接池生命周期 | **维持现状**：池子按需新开连接时要用密码。若改成每次重新解析，后台补连接时会触发解锁，得不偿失 |
| SDK 请求 DTO → 进程内插件 | 由插件决定 | 与今天手输密码的信任等级相同，在 [12 威胁模型](../plugins/12-security-threat-model.md) 中写明 |
| `tab.Profile` | 标签生命周期 | 引用配置的 `tab.Profile` 不含解析出的密码，重连会重新解析；手输密码的副本含密码（与今天一致） |

### 5.10 与同步、导入、导出等流程的交互

| 流程 | 行为 | 需要改代码吗 |
|---|---|---|
| Gist 推送（未加密） | 清空 `Password`，引用照常上传 | 否 |
| Gist 推送（端到端加密） | 引用配置在库里本来就没有 `Password` | 否 |
| Gist 拉取 | 远端带引用、本机有旧密码时，`:623` 会把密码拷回，仓储不变量随即剥掉 | 否 |
| Gist 拉取到一台没配置该 provider 的机器 | 连接时抛 `NotInstalled` 或 `ProviderDisabled`，退回弹窗手输 | 否 |
| 会话导入 | 导入器不产出引用 | 否 |
| 复制配置 | `Clone()` 复制引用，两条配置指向同一条目，符合预期 | 否（补 `Clone` 即可） |
| 外部拉起 | 请求不带密码时复用已存配置，已存配置带引用即可正常解析 | 否，回归测试一遍 |
| AI / 插件连接提议 | 提议带明文密码，走配置弹窗保存，不涉及引用 | 否 |
| 配置导出 / 导入 | 若 provider 设置放在 `AppSettings` 里，本机路径会被导出；按 §16 N4 放在 `AppSettings` 之外则不受影响 | 视 N4 而定 |

### 5.11 审计与日志

**审计**（`IAuditLogService`，`Category = "security"`）只记**失败与解锁事件**，避免每次连接都多写一条：

| Action | 时机 | Detail |
|---|---|---|
| `credential-failed` | 解析抛出 `CredentialProviderException` | `{providerId} {kind}`，**不写条目标题** |
| `vault-unlocked` | 解锁成功 | `{providerId} {targetName?}` |
| `vault-unlock-failed` | 解锁口令错误 | `{providerId}` |
| `vault-forgotten` | TTL 到期、手动锁定、网络恢复时清缓存 | `{providerId} {reason}` |

`ProfileId` 填写对应配置。写审计失败不影响连接，与 `RecordHistoryAsync` 的做法相同。

**诊断日志**：`Trace.WriteLine("[Cred] …")`，只记：

- provider id、子命令名（`item get` / `unlock` 等，**不记参数**）、耗时、退出码、`CredentialFailure` 种类；
- stderr 取前 200 个字符，并替换其中的邮箱、路径。

**永不记 stdout**。

### 5.12 连接诊断

- `HasStoredCredentials` 对带引用的配置返回 true。
- **优化建议**：诊断流程在第 4 步（认证）之前增加一步「凭据来源」。它调用 `GetStatusAsync` 报告 provider 状态，再以交互模式试解析，失败时给出 §5.8 那张表里的文案。这样用户排查「连不上」时，能分清是保险库的问题还是服务器的问题。步骤文案沿用 `DiagSvc_` 前缀。

## 6. 解锁会话缓存

### 6.1 各 provider 缓存什么

| provider | 缓存对象 | 说明 |
|---|---|---|
| 1Password | **不缓存** | 授权由桌面 App 管理：连续 10 分钟不用即失效，最长 12 小时；App 锁定时撤销全部授权（官方文档，§8.1） |
| Bitwarden | `bw unlock` 换回的 **session key** | 主密码只用一次，**不缓存主密码本身** |
| KeePassXC | **数据库口令**，按数据库别名分别缓存 | CLI 没有会话概念，每次调用都要口令 |
| 系统密钥链 | 不缓存 | 系统负责 |

### 6.2 规则

- **设置项** `UnlockCacheMinutes`：默认 **15**，`0` 表示不缓存（每次都问），上限 **480**（与 1Password 12 小时同一量级，再长就不合理了）。
- **绝对过期**：从解锁那一刻起算，不做滑动续期。滑动续期在持续使用时等于永不过期。
- **清除时机**：
  - TTL 到期（每个 provider 一个 `Timer`）；
  - 应用退出；
  - 设置页「立即锁定」按钮；
  - `bw status` 返回 `locked`（说明 session key 已失效）；
  - KeePassXC 口令被拒；
  - **`ConnectivityMonitor.Resumed`**：休眠唤醒时网卡会重新初始化并触发这个事件（§16 N6）。
- **承载与清零**：`char[]`（口令）或 `byte[]`（session key 的 UTF-8 形式）；清除时调用 `CryptographicOperations.ZeroMemory`。
- **诚实边界**：写进子进程 stdin 或 `ProcessStartInfo.Environment` 时，不可避免会生成托管 `string` 副本，GC 之前会留在堆上。这与 `SecureStringConvert.ToPlaintext` 交接点的取舍一致，在代码注释里写明，不做表面功夫。

## 7. CLI 运行器

`CliCredentialRunner`（`Infrastructure/Credentials/CliCredentialRunner.cs`）是三家 provider 共用的调用封装，全方案风险最集中的地方。

### 7.1 接口草案

```csharp
internal sealed record CliInvocation(
    string ExecutablePath,
    IReadOnlyList<string> Arguments,                          // 走 ArgumentList，绝不拼接字符串
    IReadOnlyDictionary<string, string?>? Environment,        // 只作用于子进程；值为 null 表示删除继承来的同名变量
    ReadOnlyMemory<char> StdinSecret,                         // 可空；写入后立即关闭 stdin
    TimeSpan Timeout,
    int MaxStdoutBytes = 4 * 1024 * 1024);

internal sealed record CliResult(int ExitCode, byte[] Stdout, string StderrRedacted, TimeSpan Elapsed);

internal sealed class CliCredentialRunner
{
    Task<CliResult> RunAsync(CliInvocation invocation, CancellationToken ct);
}
```

`Stdout` 用 `byte[]` 而不是 `string` 返回：调用方解析完即可清零，也便于直接交给 `JsonDocument.Parse(ReadOnlyMemory<byte>)`。

### 7.2 硬性规则

| # | 规则 | 理由 / 依据 |
|---|---|---|
| 1 | 可执行文件用**设置里保存的绝对路径**，调用时不查 PATH | 防 PATH 劫持 |
| 2 | 机密**不进命令行参数** | 参数会出现在进程列表里 |
| 3 | 传入机密走 **stdin**（KeePassXC）或**只写进子进程的环境变量**（Bitwarden 的 `--passwordenv` 与 `BW_SESSION`） | 同上 |
| 4 | **绝不调用** `Environment.SetEnvironmentVariable` | ConPTY 本地终端继承 VelaShell 整个进程环境（`ConPtyShellStream.cs:223-226`） |
| 5 | 显式删除继承来的敏感变量：Bitwarden 调用删除 `BW_SESSION`（再按需写入自己的）；1Password 调用**不改动** `OP_ACCOUNT` / `OP_BIOMETRIC_UNLOCK_ENABLED` / `OP_SERVICE_ACCOUNT_TOKEN` | 用户从带 `BW_SESSION` 的 shell 启动 VelaShell 时，不该悄悄借用那个会话；1Password 的环境变量是用户的显式配置，应当尊重 |
| 6 | `UseShellExecute = false`、`CreateNoWindow = true`、重定向 stdin / stdout / stderr | 避免 Windows 上闪出控制台窗口 |
| 7 | `StandardOutputEncoding = StandardErrorEncoding = UTF8`（无 BOM）；stdin 同样用 UTF-8 写入 | 条目标题、口令可能含非 ASCII 字符；Windows 控制台默认代码页会让它们乱码（**待实测**三家 CLI 在 Windows 上的实际输出编码） |
| 8 | 超时到达时 `process.Kill(entireProcessTree: true)`；取消令牌同样处理 | 参照 `PluginProcessClient.TryKill`（`:361-374`） |
| 9 | stdout 读满 `MaxStdoutBytes` 即截断并杀进程，报 `Malformed` | 防止异常输出撑爆内存 |
| 10 | stderr 只保留前 200 个字符，并替换邮箱与路径后才允许进日志 | §5.11 |
| 11 | **stdout 永不进日志、永不进异常消息** | 可能含密码 |
| 12 | 全程在线程池上执行，不占 UI 线程 | 1Password 的 Windows Hello 窗口由它自己的 App 弹出，我们只 await |
| 13 | 同一个 provider 的 CLI 调用串行执行（与 §5.6 解锁串行化共用一把锁，或单独一把锁） | `bw` 与 `keepassxc-cli` 并发访问同一数据目录或数据库的行为**待实测**；串行最稳 |
| 14 | 默认超时：交互式 90 秒（给 Windows Hello / YubiKey 触摸留时间），非交互式 20 秒，状态探测 5 秒 | 可在 provider 实现里覆盖 |

### 7.3 可执行文件定位

- **优先**用设置里保存的绝对路径；文件不存在则报 `NotInstalled`。
- **自动探测**（设置页「自动检测」按钮，或首次打开设置页时执行一次）：
  - 在 PATH 里查找，参照 `LocalShellCatalog.FindOnPath`（`:53-76`）。那里只在 Windows 上生效、且不处理 PATHEXT，这里要写成跨平台版本（Windows 依次试 `.exe` / `.cmd`，`bw` 用 npm 安装时是 `bw.cmd`，**待实测**）。
  - 再查各家常见安装目录（**待实测**后再写死，不凭记忆）。
  - 探测结果写回设置并显示出来，**由用户确认后才启用**，不静默启用。
- **签名校验（可选，不作为 v1 必做项）**：
  - 仓库目前没有 Authenticode 校验的先例。
  - Windows 上 1Password App 会自己校验连接方 `op.exe` 的 Authenticode 签名（官方文档），所以对 1Password 来说，VelaShell 侧的校验是重复劳动。
  - Bitwarden / KeePassXC 没有类似机制。若要做，Windows 用 `WinVerifyTrust`；其它平台暂不做。

### 7.4 JSON 解析

- 用 `JsonDocument` 按需取字段（参照 `HttpPluginMarketClient.cs:104,229` 的 DOM 写法），**不定义强类型模型**，以容忍 CLI 输出字段的增减。
- 解析完成后，把 stdout 字节数组清零。

## 8. 三家 provider 规格

### 8.1 1Password（`op` v2）

**已核实的事实**

- **App 集成**：在 1Password App 的「设置 → 开发者 → Integrate with 1Password CLI」开启；支持 Mac / Windows / Linux，Linux 需要 PolKit；Windows 上用 Windows Hello。
- **授权时长**：「连续 10 分钟不活动即过期」「硬上限 12 小时」「每次使用自动续期」。
- **授权作用域**：macOS / Linux 限定在一个终端会话内，并延伸到该窗口的子 shell；**「On Windows, commands executed in a sub-shell require separate authorization」**。
- **App 锁定**：「When the 1Password app is locked, all prior authorization is revoked」。
- **Windows 通信方式**：命名管道；App 会校验连接进程可执行文件的 Authenticode 签名。
- **`op item get`**：`op item get [{ <itemName> | <itemID> | <shareLink> | - }] [flags]`，支持 `--fields label=username,label=password` 与 `type=` 过滤、`--vault`、`--reveal`（人类可读输出里显示被隐藏的字段）、`--otp`、`--include-archive`。**官方建议按 ID 寻址**，可以避免限流和同名歧义。
- **`op item list`**：支持 `--vault`、`--categories`、`--tags`、`--favorite`、`--long`、`--include-archive`。**JSON 字段结构文档没有写明**。
- **多账户**：`--account` 标志，或 `OP_ACCOUNT` 环境变量。
- **`op whoami`**：「没有已认证的账户时返回错误」。
- **`OP_BIOMETRIC_UNLOCK_ENABLED`**：用于开关 App 集成。

**设计**

| 操作 | 命令 | 备注 |
|---|---|---|
| 状态探测 | `op --version`；再 `op account list --format json` | **不调用 `op whoami` 或 `item` 命令**，以免设置页一打开就弹 Windows Hello。`account list` 本身会不会触发授权**待实测**；若会，状态探测只做到 `--version` 为止，登录状态标为 `Unknown` |
| 搜索 | `op item list --categories Login --format json [--account <id>] [--vault <id>]` | 会触发授权（用户主动打开选择器，可以接受）。结果在本次选择器会话内缓存 |
| 补用户名 | 用户选中条目后执行 `op item get <itemId> --vault <vaultId> --account <accountId> --fields label=username --format json` | 列表 JSON 里有没有用户名没有文档，不依赖它 |
| 解析 | `op item get <itemId> --vault <vaultId> --account <accountId> --format json` | 取完整条目 JSON，**优先按字段的 `purpose`（`USERNAME` / `PASSWORD`）挑选**，找不到再按 `label` 回退。这样用户改过字段标签也能正确取值。`purpose` 字段是否存在**待实测**；JSON 输出里被隐藏的字段是否需要 `--reveal`**待实测**（社区反馈 JSON 直接含值），实测前一律带上 `--reveal` |

**失败映射**（错误文本**待实测**后补全匹配规则）：

| 情形 | `CredentialFailure` |
|---|---|
| 可执行文件不存在 | `NotInstalled` |
| 没有账户，或 App 集成未开启 | `NotSignedIn` |
| 用户在 Windows Hello 弹窗点了取消 | `UnlockCancelled` |
| 条目不存在或已归档 | `NotFound` |
| 超时 | `Timeout` |

**⚠️ 第一实测项：Windows 上的授权作用域**

官方只说「子 shell 需要单独授权」，没有说明由 GUI 进程拉起的 `op` 怎么算。可能的结果：

- (a) 以 VelaShell 进程为「终端会话」，10 分钟内多次调用只授权一次 —— 理想情况；
- (b) 每次调用 `op` 都要一次 Windows Hello —— 必须把一次连接压到**只调用一次** `op`（补用户名与解析合并成同一次 `item get`），选择器搜索也要缓存结果；
- (c) 其它情况。

实测结果写回本节，并据此决定是否要合并调用。

**要避开的坑**

- 用户环境里若有 `OP_SERVICE_ACCOUNT_TOKEN`，`op` 会改用服务账户，不走 App 集成。这是用户自己的配置，状态探测时应当识别出来并显示「服务账户模式」。
- 1Password 的 SSH Agent 属于私钥线，与本期无关。

### 8.2 Bitwarden（`bw`）

**已核实的事实**

- **`bw status`** 返回 `{ serverUrl, lastSync, userEmail, userId, status }`。`status` 取值为 `"unlocked"` / `"locked"` / `"unauthenticated"`。调用前 CLI 会先尝试一次自动解锁，失败不抛异常。
- **全局参数**：`--raw`（原始输出）、`--response`（JSON 包装）、`--quiet`、`--nointeraction`（「Do not prompt for interactive user input」，内部会设置 `BW_NOINTERACTION=true`）、`--session <key>`（内部等价于设置 `BW_SESSION`）、`--cleanexit`、`--pretty`。
- **`bw unlock [password]`** 用于「Unlock the vault and return a new session key」，支持 `--check`、`--passwordenv <var>`、`--passwordfile <path>`。session key 在 `bw lock` 或 `bw logout` 之前一直有效。
- **`bw lock`** 用于「Lock the vault and destroy active session keys」。
- **`bw list items`** 支持 `--search`、`--folderid`、`--url`。**输出是完整条目，包含 `login.password`**。
- **`bw get item <id>`** 返回完整条目 JSON；另有 `bw get password <id>` / `bw get username <id>`。
- **`bw sync`**（`-f` 强制全量、`--last` 查看上次同步时间）；**`bw config server <url>`**。
- **登录方式**：邮箱密码（支持两步验证）、`--apikey`（`BW_CLIENTID` / `BW_CLIENTSECRET`）、`--sso`。
- **安装方式**：原生可执行文件（Windows / macOS / Linux x64）、npm、snap、Chocolatey。它是 Node.js 应用。

**设计**

| 操作 | 命令 | 备注 |
|---|---|---|
| 公共约定 | 每次调用都带 `--nointeraction` | stdin 被重定向时，CLI 若等待交互输入就会一直挂到超时 |
| 状态探测 | `bw status --nointeraction`（子进程环境里删掉 `BW_SESSION`） | 从 `status` 映射出 `NotSignedIn` / `Locked` / `Ready`；`userEmail` 用于解锁弹窗的 `TargetName` |
| 解锁 | `bw unlock --passwordenv VELA_BW_PW --raw --nointeraction`，`VELA_BW_PW` 只写进子进程环境 | stdout 就是 session key，放进 §6 的缓存。**不用 `--passwordfile`**（会落盘） |
| 搜索 | `bw list items --search <q> --nointeraction`，环境变量 `BW_SESSION=<key>` | ⚠️ **输出含密码**：流式解析成 `CredentialItemSummary`（`id`、`name`、`login.username`、`login.uris[0].uri`、`folderId`）后立即丢弃，stdout 字节数组清零。**选择器一次会话内只调用一次**，之后在本地过滤 |
| 解析 | `bw get item <id> --nointeraction`，`BW_SESSION=<key>` | 取 `login.username` / `login.password`；条目类型不是 login 时报 `MissingField` |
| 同步 | `bw sync --nointeraction` | 选择器里的「同步」按钮手动触发，**不自动同步** |
| 锁定 | **不调用 `bw lock`** | 它会销毁 CLI 数据目录中的所有会话，连用户自己终端里的 `BW_SESSION` 也一起失效。VelaShell 只丢弃内存中的 session key |

**失败映射**：

| 情形 | `CredentialFailure` |
|---|---|
| `unauthenticated` | `NotSignedIn`（登录不在本期范围，提示用户自己在终端执行 `bw login`） |
| `locked`，且处于非交互模式 | `Locked` |
| 解锁口令错误（错误文本**待实测**） | `UnlockFailed`，交互模式下再弹一次，最多 3 次 |
| `get item` 找不到 | `NotFound` |

**要避开的坑**

- 自建服务器由用户自己执行 `bw config server` 配置，VelaShell 不代劳。
- 用 npm 安装时，Windows 上的入口是 `bw.cmd`，要经 `cmd.exe` 转一层（**待实测**）。确实如此的话，参数转义要格外小心，或者建议用户改装原生版。
- Node 应用每次启动都有开销，具体耗时**待实测**。选择器搜索要做防抖，并复用结果。

### 8.3 KeePassXC（`keepassxc-cli`）

**已核实的事实**

- **口令读取**：`Utils::getPassword` 用 `QTextStream` 从 **stdin 读一行**，读取前后切换回显；**管道输入同样可用**。提示文字「Enter password to unlock %1: 」写到 **stderr**，`-q` 时写到空设备。
- **数据库参数**：`-k/--key-file <path>`、`--no-password`、`-y/--yubikey <slot[:serial]>`（slot 只能是 1 或 2）、`-q/--quiet`。
- **`show`**：支持 `-a/--attributes <name>...`、`-s/--show-protected`、`--all`、`-t/--totp`、`--show-attachments`。
  - 带 `-a` 时**每行输出一个值**；
  - 属性名**区分大小写，并支持部分匹配** —— 有歧义时报错「ERROR: attribute %1 is ambiguous, it matches %2.」；
  - 不带 `-a` 时，受保护属性显示为 `PROTECTED`。
- **条目寻址**：`Group::findEntryByPath` **只接受路径，不支持 UUID**。标题重名时**返回第一个匹配项**。找不到时报「Could not find entry with path %1.」，退出码为 `EXIT_FAILURE`。
- **`ls`** 支持 `-R/--recursive`、`-f/--flatten`；**`search <database> <term>`** 的输出格式没有文档；**`open`** 进入交互式 shell 模式。
- **没有 JSON 输出**。

**设计**

| 操作 | 命令 | 备注 |
|---|---|---|
| 状态探测 | `keepassxc-cli --version`；再检查设置里每个数据库文件是否存在、是否可读 | 不打开数据库 |
| 搜索 | `keepassxc-cli ls -R -f -q [-k <keyfile>] [-y <slot>] <db>`，口令经 stdin 传入 | 输出扁平化的条目路径（分组以 `/` 结尾，**待实测**具体格式），在本地过滤。结果**只含路径，不含机密**，在该数据库的解锁会话内缓存 |
| 补用户名 | 选中后执行 `show -q -a UserName <db> <path>` | 或者在搜索阶段不显示用户名，以减少 KDF 次数（见下文「性能」） |
| 解析 | `keepassxc-cli show -q -s -a UserName -a Password [-k] [-y] <db> <entryPath>`，口令经 stdin 传入 | 第一行是用户名，**其余行拼起来是密码**（防止密码里本身带换行）。`-s` 与 `-a` 同时使用在各版本上的行为**待实测** |
| 选择时查重 | 同一路径在 `ls` 结果里出现不止一次时，选择器提示「存在同名条目，可能取到其它条目」，并建议用户先在 KeePassXC 里改名 | 因为 CLI 按路径取第一个匹配项 |

**失败映射**：

| 情形 | `CredentialFailure` |
|---|---|
| 数据库文件不存在或不可读 | `NotInstalled`，文案改为「数据库文件不可用」 |
| 数据库打开失败（口令错误时只有笼统的打开错误，**待实测**具体文本） | `UnlockFailed` |
| 「Could not find entry with path」 | `NotFound` |
| 「is ambiguous」 | `Malformed`，并提示是属性名冲突 |
| 触摸 YubiKey 超时 | `Timeout` |

**性能：每次调用都要重新派生密钥**

每次调用 CLI 都会重新执行一次 KDF。KeePass 数据库默认的 Argon2 参数就是**有意设计得耗时**，具体耗时取决于数据库设置，**待实测**。于是一次「搜索 + 补用户名 + 解析」就要执行三次 KDF。两个方案：

- **v1（推荐）**：逐次调用，但尽量合并 —— 解析只调用一次 `show`（同时取两个属性），选择器里只调用一次 `ls`，用户名只对选中的那一条去取。
- **后续优化（§16 N8）**：每个解锁会话保持一个 `keepassxc-cli open` 交互进程，经 stdin 发送命令，只做一次 KDF。代价是数据库在子进程里一直保持解锁、交互模式的输出更难解析，而且进程常驻。等 v1 实测证明确实慢到影响使用再做。

### 13.2 CLI 运行器

逐条对应 §7.2 的硬性规则：

- 参数里不出现传入的机密；
- 调用结束后，当前进程环境里不存在 `BW_SESSION` 或 `VELA_BW_PW`；
- 继承来的 `BW_SESSION` 在子进程里被删除；
- stdin 写入后被关闭；
- 超时会杀掉整个进程树（假 CLI 会再起一个子进程，断言两者都被结束）；
- stdout 超过上限时截断并报 `Malformed`；
- stderr 中的邮箱与路径被替换；
- 非 ASCII 字符往返不变。
