`feat/sftp-r2b` 已补齐：本地/远端目录后退与前进（各 50 步、仅面板实例内）、当前目录名称过滤、F5/F2/Delete、过滤框 Esc/Enter、本地新建空文件与双击系统打开、远端列宽和双栏比例跨重启记忆，以及 SSH 文件栏右键「在此处打开终端」。下文旧差距描述中的这些项目不再是待办；双击仍不是传输快捷方式。键位与焦点条件见[快捷键参考](快捷键参考.md)。插件协议的链接字段、修改时间和服务器摘要也已接入，创建符号链接仍无契约。

## 一、先看结论

VelaShell 目前是一个**做得相当扎实的单向文件传输器**，但还不是一个**双栏文件管理器**。

传输管道本身的质量明显高于同类小工具：递归上传/下载规划、四种冲突策略、断点续传（含起点核实）、
限速、并发、进度浮窗、传输日志、取消语义、`LocalPathSafety` 路径穿越校验。
远端栏的表格（7 列、可排序、可隐藏、可拖宽、双击自适应）也超出预期。

差距集中在三个层面，**处理方式完全不同，不要混在一起排期**：

| 类别 | 含义 | 用户感知 | 建议 |
|---|---|---|---|
| **A. 接线债** | 代码写好了，但没接到双栏这条路 | **像 bug** | 优先修，代价极低 |
| **B. 能力缺失** | 确实没做，但架构支持 | 功能少 | 按需求排期 |
| **C. 架构级缺失** | 连接口层都没预留 | 与 WinSCP 的本质差距 | 需要专门设计 |

### 3.2 文件操作

| WinSCP 能力 | VelaShell | 说明 |
|---|---|---|
| 新建文件夹 / 文件 | ✅ 远端齐全 | 本地栏**只有新建文件夹，没有新建文件** |
| 重命名 | ✅ 双侧 | |
| 删除（递归 + 进度 + 取消） | ✅ 双侧 | 质量不错，远端还有加权进度。**SSH 会话上删目录走一条 `rm -rf` 快路径**（2026-09-20，`Transfer.UseRecursiveDeleteCommand`，默认开）：SFTP 递归的往返次数与文件数成正比，`rm -rf` 是一次往返；命令不可用或退非零码即回退 SFTP 递归。代价是这条路上没有逐条进度（进度条转不确定态），二次确认不受影响 |

| 本地文件属性 / 权限 | ❌ 无 | 本地栏右键：刷新、打开、上传、重命名、新建文件夹、删除 |

## 四、C 类：架构级缺失

这三项**连接口层都没有预留**（`ISftpService.cs` 全文 82 行无相关签名），需要专门设计。
（C1 已于 2026-09-12 完成，见第七节。）

### C1. 同步与目录比较 —— ✅ 已实现（2026-09-12）

WinSCP 的三大同步能力现已具备，适用于 SFTP、FTP、FTPS 双栏文档，规则见[第七节](#七附2026-09-12-目录比较与同步)：

- **目录比较**：双栏文档工具条「比较目录」，在两栏各自选中不同的条目（仅当前一层，与 WinSCP 同名命令同一口径）
- **同步（单向 / 双向 / 镜像 / 仅时间戳）**：扫描 → 预览（可逐项取消勾选）→ 确认删除 → 批量执行 → 自动复查
- **保持远程目录最新**：监视本地改动自动上传

~~原判断：零行代码，需要新增比较结果模型、差异计算、预览 UI、执行引擎。~~
差异计算默认**先比 SHA-256**（服务器端算摘要），不支持或出错时回退到大小 + 修改时间（见 7.4）。

### C2. 搜索能力 —— ✅ 已实现（2026-10-24）

~~`ISftpService` 需要新增递归搜索 API。注意远端递归遍历的成本，
需要流式返回 + 可取消（现有 `ListDirectoryAsync` 是一次性返回 `List`，不适合直接递归）。~~

最后**没走 `ISftpService` 的递归遍历**，而是经 SSH 会话的 exec 通道跑一条 `find` / `grep`：遍历在服务器本机做，一次往返，
结果逐条流回来（`Core/Sftp/RemoteSearch` + `RemoteSearchService`）。口径：

- **入口**：SSH 会话的文件面板（终端侧栏、单栏 SFTP 文档、双远端里是 SSH 的那一栏）的工具条放大镜、空白处右键「搜索远端文件…」、
  目录行右键「在此目录中搜索…」（以该目录为起点）。一个面板一扇非模态窗口，面板拆掉（标签关闭、会话断开）窗口随之关闭。
- **先判 POSIX**：按主机缓存判远端 shell；Windows 的 cmd / PowerShell、csh 一类说「不支持」，exec 被禁、只开 SFTP 的账号说「判定不了」，
  这两种**一条命令都不发**。bash、zsh、POSIX sh、fish 可以搜。
- **不留注入口**：脚本本体是写死的常量，用户输入只作单引号位置参数（`sh -c '<脚本>' vela-search '<根>' '<模式>' …`），引号按登录 shell 的规则写。
- **只用 BusyBox 也有的选项**（含 `-maxdepth`、`tr`、`grep -q`）；从 `/` 起找才跳过 `/proc`、`/sys`、`/dev`；不跟随链接。按名字是 `find` 的通配（不带通配符按「名字含有」），
  按内容只做字面匹配（`grep -F`），不提供正则。
- **上限**：500 项、2 分钟，都写死；收满或超时如实说「结果不全」，用户随时可停、关窗即停。
- 已知限制：裁掉了 `find -exec … +` 的极老 BusyBox 上按内容搜索为 0 项、名字里带换行的仍拆成两条（2026-10-25 起结果按会话编码解、搜索参数也按会话编码交给服务器，名字里的换行各算一条；此前 GBK 服务器上的中文名在结果里显示成替换字符、名字里含换行的拆成两条）。
- 「当前目录过滤框」仍没有（3.5）。

## 七、附：2026-09-12 目录比较与同步

适用于 SFTP、FTP、FTPS 双栏文档（插件协议的文件文档同样能用，限制见 7.5）。入口在双栏文档顶部的工具条；
终端侧边栏里的文件浏览器没有本地栏，不提供这两个入口。

### 7.1 比较目录（不递归）

- 比较两栏**当前所在的目录**这一层，比较依据取同步窗口上次用的设置（默认修改时间 + 文件大小）。
- 本地栏选中：只有本地有的、本地较新的；远端栏选中：只有远端有的、远端较新的；
  时间相同而大小不同的、以及冲突的，两栏都选中。
- 工具条右侧给出一句结论（「本地 N 项不同 · 远端 N 项不同 · N 项相同」），任一栏换了目录即清除。
- 远端栏隐藏点文件时，本地栏的点文件也不参与比较，免得每个 `.git`、`.env` 都被标成「只有本地有」。

### 7.2 同步窗口

| 选项 | 取值 | 说明 |
| --- | --- | --- |
| 方向 | 本地 → 远端 / 远端 → 本地 / 双向 | 双向时模式固定为「同步文件」，且从不删除 |
| 模式 | 同步文件 / 镜像文件 / 仅同步时间戳 | **同步**：传新增的、较新的、大小不同的，不覆盖较新的目标；**镜像**：只要不同就覆盖，哪怕目标更新；**时间戳**：不传内容，两边都有且大小相同、时间不同的文件，把目标时间改成源的 |
| 比较依据 | SHA-256 校验（默认勾选）、修改时间、文件大小 | 三样都不选 = 只补齐缺失的；SHA-256 的口径见 7.4 |
| 删除多余文件 | 仅单向 | 删除只在目标一侧存在的条目；目录整棵删除，其下条目不再单列；执行前二次确认 |
| 仅已存在的文件 | — | 只更新两边都有的文件，不新建任何东西 |
| 文件掩码 | WinSCP 写法 `包含 \| 排除` | `;` 分隔多个掩码；以 `/` 结尾的是目录掩码；中间含 `/` 的按相对路径匹配；`*` `?` 不区分大小写；`*.*` 等同 `*`。被排除的目录**不扫描**，也就不会被删除 |

流程：**比较**（两边并行扫描，状态栏显示已扫描的目录数，可取消）→ **预览**（每一步一行：操作、路径、两边的大小与时间，
可逐项取消勾选；改动任何选项都会作废预览）→ **同步** → **自动复查**（结论写明「没有剩余差异」或「仍有 N 项待同步」）。

执行规则：

- 顺序：建目录 → 改时间 → 传文件 → 删除。**中途取消后不再执行删除。**
- 传文件与普通上传下载走同一条管道（传输浮窗、全局并发上限、传输日志），但**不走「文件已存在时」的冲突策略，
  也不做续传探测** —— 预览就是确认；目标比源小正是「内容不同」的常态，不能当半截文件去续传。
- 传完**总是**回写修改时间（不看「保留时间戳」设置）：上传后用 SFTP setstat / FTP `MFMT` 把远端时间对齐本地，
  下载后把本地时间对齐远端。不回写的话，下一次比较会把刚传上去的文件判成「远端较新」。服务器不支持时窗口里给出提示。
- 从远端名字拼出的本地路径逐段校验：Windows 上不合法的名字（如 `a:b`、`CON`）报错跳过，而不是写到别处。
- 父目录由执行器逐级补齐：在预览里取消勾选「新建目录」、只留下其中的文件，照样能传。

### 7.3 保持远端目录最新

- 恒为本地 → 远端，沿用窗口里的文件掩码、比较依据与「删除多余文件」（勾了删除会先确认）。
- 开始时先完整对齐一次；之后监视本地目录树，改动防抖 1 秒后**只对变化所在的那一层目录**重新比较，
  新出现的目录（解压、`git clone`）整棵比较；监视缓冲溢出（事件被丢）时整棵重对一遍。
- 列表区换成活动记录（最新在上），记下每次上传与删除；关闭窗口或关闭文档即停止。

### 7.4 比较口径

- **SHA-256 优先**（2026-09-13 补上）：两边都有、**大小相同**的文件先比内容摘要（大小不同已经证明内容不同，不必再读）。
  - 摘要相同 = 同一个文件，**时间不同也不传**（`git checkout`、解压、`touch` 之后不再整片重传）；
    摘要不同 = 内容确实变了，由修改时间判断哪边较新，时间也相同时算「内容不同」（单向照传，双向不动）。
  - 远端摘要在**服务器上算**，不经网络传内容：SFTP 经 SSH exec 通道跑 `sha256sum`（没有则 `shasum -a 256`），
    每批最多 200 个路径；FTP / FTPS 用 `HASH`（SHA-256）或 `XSHA256`。先算远端，服务器不支持时本地一个字节都不读。
  - **回退**：服务器整体不支持或出错（纯 SFTP 账号禁了 exec、主机没有这两个工具、Windows 远端、FTP 服务器不提供这两条命令、
    插件协议）→ 这一轮全部按大小与修改时间比较，窗口附注写明原因；单个文件读不了 → 只有它回退，附注写明「N 个中有 M 个」。
    只勾了 SHA-256 而没勾时间与大小时，回退按两样都比。
  - 时间戳模式下也生效：算出摘要而内容不同的文件，不会被改时间掩盖差异。
  - 摘要按「路径 + 大小 + 修改时间」缓存到窗口 / 文档关闭：同步后的自动复查只重算刚传过的文件（等于顺带做了传输后校验）。
  - 「比较目录」同样先比 SHA-256，回退时结论后面带一句提示。
- **时间精度**：两边先截到较粗的一级再比。SFTP 为秒；FTP 的 Unix LIST 只给到分钟（半年以前的文件只给到日期），
  按原始值推断精度；容差 1 秒（吸收 FAT/exFAT 的 2 秒粒度）。FTP 连接配了服务器时区时，LIST 的时间先按偏移换算，
  按日比较时两边放进**服务器那本日历**截断（半年前的文件 LIST 只给服务器当地日期，按本机日历截会把晚上改的文件落在相邻两天）。
- **大小写**：Windows / macOS 上路径配对不区分大小写；远端有两个只差大小写的名字时标为冲突、不处理。
- **类型冲突**：一边是文件一边是目录，标为冲突，其下子项不再比较（否则勾上删除会去删一棵没打算动的树）。
- **链接**：两边都不进入指向目录的链接（跳过的个数会提示，与文件夹下载同一口径）；远端指向文件的链接按文件处理；
  本地只跳过真正的符号链接与目录联接，OneDrive「按需下载」的占位文件照常参与。

### 7.5 未做 / 已知限制

- **SHA-256 的代价**：大小相同的文件要在两边各完整读一遍（本地读盘、远端服务器读盘），大目录第一次比较会明显变慢；
  不需要时可取消勾选。缓存不跨窗口：内容改了但大小与修改时间都没变（刻意 `touch -r`）的文件，在同一个窗口里第二次比较时会用到旧摘要。
- 同步选项只在同一个文档标签里记住，不写进设置，重启后回到默认。
- ~~**FTP 时区**：LIST 的时间按服务器当地时间给出、按本机时区解释。服务器与本机不在同一时区时，时间比较会整体偏移 ——
  这时请只勾「文件大小」。WinSCP 在会话设置里提供「时区偏移」，VelaShell 暂无此项。~~ —— 2026-10-24 已解决：在 FTP 连接的「高级」页设
  「服务器时区」（`FtpSettings.ServerUtcOffsetMinutes`，存服务器时钟的 UTC 偏移，默认「与本机相同」即旧行为）。只挪 LIST 给的服务器墙上时间；
  MLSD / MLST 本来就是 UTC，原样用；文件面板的时间列照旧显示服务器自己的钟。同步窗口（含保持远端最新）、单栏与双远端的「比较目录」都按它换算。
  剩下一点：固定偏移不随服务器的夏令时变化，那半年要手动改一次（WinSCP 也一样）。
- 不支持 `MFMT` 的 FTP 服务器与插件协议，上传后无法对齐远端时间：单向「本地 → 远端」不受影响（远端较新不会被当成要上传），
  但**双向同步会把刚上传的文件再下载回来**，窗口会提示这一点。
- 「保持最新」只有本地 → 远端（与 WinSCP 相同）。

## 八、附：2026-09-28 远程 + 远程双栏（#524）

WinSCP 的 Commander 界面两栏都可以指向远端、FileZilla 可以开两个远程标签互拖；VelaShell 原先的双栏固定是「本地 + 远程」，
两台服务器之间搬文件只能先下载再上传。现在资源管理器里 Ctrl 选中两条连接、右键「在双栏 SFTP 中打开」，得到一个两栏各连一台机器的文件标签。
交互细节见 [交互与界面规格.md](交互与界面规格.md) §3（多选）与 §6.2。

### 8.1 为什么是「经本机中转」

- **server direct 的边界**：普通 SFTP 没有通用的跨服务器复制操作。通过 SSH 在一端执行 `scp` / `sftp` / `rsync` 是另一种方案，需要服务器间网络互通、所需工具、目标凭据和主机密钥校验（不能以关闭校验代替）；FTP 的 FXP 则取决于两端服务器支持、安全策略及网络条件，不能假定可用。本次不实现这两类直接互传，也不向远端转发凭据或 SSH agent。
- **FTP/FTPS 源先完整缓存（2026-10-28）**：双远端中任一侧作为 FTP/FTPS 源时，使用高级 `DownloadStream` → 完整 cache → `UploadStreamAsync`，不再直接把 FTP `OpenReadAsync` 数据流喂给目标。所有文件（包括空文件、小文件、大文件及长度未知的文件）统一使用 `UserPathResolver.Home/.velashell/temp` 下随机命名、独占打开、带 `DeleteOnClose` 的临时文件；不再采用 ≤4 MiB 内存缓存或 large/unknown 系统临时目录分流。该目录所在磁盘须有容纳完整文件的空间，内容可能敏感。本地缓存磁盘失败归为永久错误，不走自动重试。
- **先 prepare、后 target**：源完整下载、缓存 `Flush`、适用的长度检查及最终 FTP 完成回复全部成功，缓存才可交给目标；在此之前不触碰目标文件，包括上传打开、截断、续传写入及失败清理。准备期间显示下载准备阶段，缓存下载字节不计入 target ACK；上传进度仍按目标确认记账，最终满格须等上传及收尾成功。源错误/取消不得变成 EOF，目标提前返回不得冒充完整消费。
- **缓存生命周期**：缓存属于单次 `Run`。同一 Run 的自动 target retry 复用已准备成功的缓存；只有 source prepare 失败后的自动重试才重新下载准备。手动 retry 是新 Run，不能复用旧缓存；冲突 rename、最终失败、取消、成功均释放缓存，临时文件关闭即删除，不跨运行保留。缓存清理与远端半截目标的保留/清理策略分开。
- **未改变的路径**：SFTP → SFTP 保留原有 `OpenReadAsync` → `UploadStreamAsync` 流式路径与 seek 续传核验。插件非 seek 源仍用 `BufferedRelayReadStream`：256 KiB 分块，每文件 4 MiB 总预算包含生产者、队列、消费者持块；已知正长度 ≤4 MiB 时先完整校验与源收尾，更大/未知长度则首块成功后经有界队列边读边写、满时背压。取消或失败时停止并等待生产者、清零归还块。默认三路的约 12 MiB 是这类预读缓冲的预算，不是 FTP 临时磁盘上限。同会话「复制到」仍是另一条路径。

- **完成门禁（2026-10-28）**：源 stat 为正长度时，中转核对实际读取长度，提前 EOF 或长度不符按失败处理；不改变 `UploadStreamAsync` 的 length 仅作进度分母的通用契约。FTP/FTPS 完整缓存路径的源完成门禁在触碰目标前通过；SFTP/插件流式路径仍须等目标上传与源流收尾均成功才转发最终满格进度。FTP 下载必须消费并验证最终完成回复后才归还连接租约；异常、取消、提前弃读或收尾不可信的连接不复用。失败目标仍遵循既有续传与清理设置，不提供原子替换或全文件哈希保证。

- **重试回归续修（2026-10-28）**：FTP 单文件 stat 与打开读流在持租约时先切 Binary 再取 SIZE，不把 LIST/MLST 的显示大小和另一种传输模式下的大小同时当精确真值；SIZE 不支持则使用既有未知长度语义，完成回复校验不取消。源读取失败不被目标 Flush/CLOSE 的次异常覆盖，另保留目标 durable 水位供续传记账。开启传输日志后，失败尝试在退避前写入脱敏结构化 `ATTEMPT_FAILED` 记录（错误类型链/数值，不写异常消息与服务器正文），重试后成功仍可追查。0B 进度可能只是小文件仍在 SFTP 缓存、首个 WRITE 尚未确认，不代表源未读取。正常批量回归必须检查首次成功与 RETR/OPEN 次数，不能只看最终哈希或把 mock 目标当真实 SFTP 互操作。

- **CI 跨平台续修（2026-10-29）**：已知 binary SIZE 的下载若以 `426` 中断且实际长度不符，保留 `RemoteTransferLengthException` 及预期/实际字节数；FluentFTP 在关闭数据流时抛出的嵌套命令异常不能掩盖该诊断。本地目标写入异常与取消仍优先，不改变 busy retry 或未知长度语义。环回 FTP 测试端的控制连接设置 `NoDelay`，避免 Linux 的 Nagle/延迟 ACK 给每个文件叠加约 40 ms；保留 2000 文件覆盖与默认 60 秒测试超时。

### 8.2 已知限制

- **续传取决于源与目标能力**：FTP/FTPS 完整缓存已可 seek，可供目标尾部校验与续传使用，不再限于 SFTP 源；这不等于所有目标支持续传，仍受目标协议/实现及续传设置约束。SFTP → SFTP 原有 stream/seek 核验不变。插件非 seek 源仍不能定位核验，插件流式上传也不因此获得续传；核实不了时按同名冲突处理，不悄悄整份重传。
- **未知 SIZE 的完整性限制**：不支持 binary `SIZE` 时仍验证下载与最终完成回复，但无可信预期长度就无法证明没有短读或源本应非空；服务端若谎报完成，完整缓存也不能保证识别 0B/短文件。不是全文件哈希保证。
- **证据边界**：已确认的代码缺陷与可控协议复现，不等于已确认用户真实现场的唯一根因。没有现场复现证据，也不声称本轮已测真实 OpenSSH；协议测试端或 mock 的成功不能替代真实服务器互操作结果。缓存统一落盘不等于已根治用户报告的约 2% 失败。
- **没有同步窗口**：「同步…」与「保持远端最新」按「本地 ↔ 远端」设计，这类标签不提供；「比较目录」提供，按大小与修改时间（不做 SHA-256）。
- **插件文件协议**（2026-09-28 补上）：S3、WebDAV 这类插件协议可以进双栏。作为源，靠 SDK 本来就有的 `OpenReadAsync`；作为目标，要插件兼实现 `IProtocolStreamUpload`（SDK 2.0.6，见 [../sdk/sdk-reference.md](../sdk/sdk-reference.md) §5），没实现的那一栏只能作为源。工作台（Redis…）与终端协议（Telnet…）进不了。
- 只开「恢复会话」时启动不恢复这类标签（逐条重连记的是单条配置）；开了「按上次的分屏恢复」时随布局一起恢复（两条配置都还在库里时）。
