# Release process (dotnet new templates)

> This page covers how **this repository** is released. For the contract SDK see
> [velashell-plugin-sdk](../sdk/release-process.md);
> for `vela-plugin` and `VelaShell.PluginSdk.Build` see
> [velashell-plugin-cli](../cli/release-process.md).

One release of this repository produces one package: `VelaShell.Plugin.Templates`.

**Upstream does not have to release along with it.** The reverse holds too: a new release of the contract SDK or
of the `.Build` package **does not require** this repository to release.

---

## 1. Two version numbers — tell them apart first

In the single-repository days they were the same number; after the split (2026-08-27) they had to be separated —
"changed the template wording" and "switched the plugin authors' build toolchain" are two completely different
kinds of change, and once they share one number there is no way to do only the first.

| Property (`Directory.Build.props`) | Meaning | Locations |
| --- | --- | --- |
| `VelaTemplatesVersion` | **The templates package's own version** — the one in the Release tag | 1: `Directory.Build.props` |
| `VelaBuildPackageVersion` | Which `VelaShell.PluginSdk.Build` release generated projects reference | 7, see below |

The seven locations of `VelaBuildPackageVersion`:

| Location | What goes wrong if it is missed |
| --- | --- |
| `Directory.Build.props` | The check baseline is wrong, so misses in the places below can no longer be detected |
| `content/velaplugin/.template.config/template.json` | New projects restore an old package — stopped at build time by `VELA1004` |
| `content/velaplugin-ui/.template.config/template.json` | Same as above |
| `content/velaplugin-protocol/.template.config/template.json` | Same as above |
| `content/velaplugin-workspace/.template.config/template.json` | Same as above |
| The `PackageReference` snippet in velashell-docs' `zh/templates/dev-guide.md` | **No error**, but the document exists to be copied, and a stale version gets pasted verbatim into other people's projects |
| The same snippet in velashell-docs' `en/templates/dev-guide.md` | Same as above |

The last two live in another repository and are **optional** locations: the script updates them only when it finds that repository through
`-DocsRoot` / `$env:VELASHELL_DOCS` / a sibling `../velashell-docs`, and skips them otherwise.

One command changes them all:

```powershell
pwsh scripts/Set-Version.ps1 -BuildPackageVersion 1.5.2
```

Without `-BuildPackageVersion` the script reads the current value from `Directory.Build.props` and keeps it, so
"just release the templates" does not need it entered again.

## 2. How to release

Two steps:

1. Stamp the version locally and merge it into `main` together with the changes:

   ```powershell
   pwsh scripts/Set-Version.ps1 1.5.1
   ```

2. **Publish a Release** on GitHub with the tag `v1.5.1` (with or without the `v` — the pipeline does a
   `TrimStart` — but using it consistently is recommended). For a pre-release, tick prerelease and use a tag
   such as `v1.6.0-preview.1`.

The pipeline's Stamp step **passes only the templates package version**; the script reads
`VelaBuildPackageVersion` from `Directory.Build.props` and keeps it — a release should not swap out the plugin
authors' build-toolchain version on the side. It changes only the working tree on the runner and **is never
written back to the repository**.

### If you forgot to stamp the version before releasing

This release is not affected (the Stamp step already covered it), but `main` is now behind: the CI "Version
consistency check" on `main` goes red once. Run it locally with the command it prints and merge a follow-up PR.

### Re-running by hand

Actions page → pick the Release workflow → Run workflow → enter the tag. Pushes use `--skip-duplicate`, so
re-running for the same tag is idempotent. To validate without pushing, tick `dryRun`.

## 3. When to raise `VelaBuildPackageVersion`

`velashell-plugin-cli` has released a new `VelaShell.PluginSdk.Build`, and you want projects generated by
`dotnet new velaplugin` to point at it — typically because that release brings something plugin authors can use
(a new MSBuild target, a fix to some packer behaviour, or a newer contract SDK that it references).

```powershell
pwsh scripts/Set-Version.ps1 -BuildPackageVersion 1.5.2
pwsh scripts/Set-Version.ps1 1.5.1        # then release the templates again to ship it
```

⚠️ **Raising it to a version that has not been published yet goes red in CI.** The smoke test really restores that
version from nuget.org, so "change the templates before `.Build` is out" is stopped on the spot instead of being
discovered when a plugin author creates a project. The order is always: publish in the cli repository first, then
raise it here.

**Not raising it is perfectly normal too.** Newly created projects keep referencing the previous `.Build`, which
is usable and not an omission — this is the normal state of things after the split.

## 4. Setting up NuGet Trusted Publishing

No API key is stored for pushing: the workflow takes this run's GitHub OIDC token to nuget.org and exchanges it
for a temporary key valid for one hour. On the nuget.org side a **policy** decides "which workflow in which
repository may push packages on my behalf".

⚠️ **After the split you need three policies, one per repository** — a policy matches on (owner, repository,
workflow file), and all three of those differ between the three repositories. A policy's owner covers **every**
package under that account, so you do not need one per package.

This repository's policy:

| Policy field | Value |
| --- | --- |
| Policy name | `velashell-plugin-templates` (anything you will recognise) |
| Policy owner | `joes_du` |
| Repository Owner | `VelaShellLabs` |
| **Repository** | `velashell-plugin-templates` |
| **Workflow File** | `release.yml` — **the file name only**, without the `.github/workflows/` prefix |
| Environment | Leave empty (the workflow does not use GitHub Environments) |

To create it: sign in to nuget.org → your user name at the top right → **Trusted Publishing** → **Add**.

### ⚠️ A new policy has a 7-day window

A policy newly created on a private repository is "**temporarily active**": it must be used for a successful
publish within 7 days or it lapses automatically (the window can be reopened at any time). The reason is that
nuget.org records the GitHub repository ID and owner ID into the policy on the first successful publish, pinning
it to that repository (a defence against resurrection attacks of the "delete the repository and recreate one with
the same name" kind) — and without a real publish it cannot get those two IDs. So **publish once as soon as the
policy is created**, even if it is only a preview.

### When no key comes back, check these three first

When the `NuGet login` step fails, nine times out of ten the policy does not match:

* Repository still says `velashell-plugin-toolchain`;
* Workflow File was entered as `.github/workflows/release.yml`;
* `NUGET_USER` was set to an email address — it must be the nuget.org **user name** (profile name).

Also, the job must keep `permissions: id-token: write`; without it GitHub does not issue an OIDC token at all.

## 5. This repository needs no secrets

It produces no assemblies, so it neither signs anything nor needs `STRONG_NAME_KEY`; pushing goes through OIDC.
So fork PRs and the main branch run exactly the same CI path.

## 6. End-to-end smoke test

Before a release, `scripts/Invoke-Smoke.ps1` runs: it installs the freshly packed templates package and, for
**all four templates**, goes through `dotnet new` → restore → `dotnet build -t:PackVpx` → read the container back →
check whether any shared assembly leaked into the plugin output directory; for `velaplugin-protocol` / `velaplugin-workspace` it also
runs the generated test project (`dotnet test`) and checks again that the plugin output directory holds only the plugin's own assembly.
Adding a template means updating both the template loop in `Invoke-Smoke.ps1` and the list of locations in `Set-Version.ps1`.

**This step is not a formality.** The templates package is a pure content package, and `dotnet pack` succeeding
proves almost nothing — everything that can really go wrong happens after it has been packed:

* `.template.config` starts with a dot, and without `NoDefaultExcludes` it never makes it into the package —
  **with no error**; the template is simply missing from the `dotnet new` list;
* The default of `sdkVersion` points at a `.Build` version that does not exist (or has not been published yet);
* The sample code in a template uses an API from a newer contract while the `.Build` package it references is
  still the old one.

All three only show up when you "really install it once, really generate a project once, really build it once".
